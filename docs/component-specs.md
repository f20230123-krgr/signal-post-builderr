# Component Specs (contracts)

Read the relevant section before implementing or modifying a component. Treat
these as interfaces — if a spec seems wrong once you're in the code, stop and
propose an update to this doc, then implement; don't silently diverge.

---

## `src/pipeline/resolve.py`

**Responsibility:** turn a bare organization number into a verified entity record.

**Input:** `org_number: str`

**Output:** `ResolvedEntity` — `org_number`, `legal_name`, `registered_address`,
`official_site_candidate: str | None`, `resolution_state` (one of the evidence
states), `source`, `retrieved_at`.

**Must:**
- Query only the official registry (or its documented public API) for this step.
- Return a `resolution_state` of `ambiguous` rather than guessing when multiple
  registry entries plausibly match.

**Must not:**
- Never fabricate a legal name or address when the registry lookup fails —
  return `not_available` / `failed`, don't leave the field silently empty
  without a state attached.

**Tests to write:** exact-match lookup, no-match lookup (→ `not_available`),
ambiguous-match lookup (→ `ambiguous`), registry-timeout lookup (→ `failed`,
retried within cap then given up cleanly).

**Added after reviewing the real challenge site:** `resolve()` also accepts an
optional `universe_entry: dict | None`. When given (this org_number's record
from `src/pipeline/universe.py`), it's used directly and no network call is
made at all — see that module's spec below for why.

## `src/pipeline/universe.py`

**Added after reviewing the real challenge site** (`signalpost-evaluation-harness.md`:
"Builderr provides the frozen official registry snapshot used for identity
anchoring"). `signalpost-company-universe-2025.jsonl.gz` is a byte-identical,
SHA-256-published file covering all 411,160 eligible companies with
name/website/legal_form/employees/municipality per org number — free to read,
identical for every entrant, no request-budget cost.

**Responsibility:** load that manifest into a dict keyed by org_number.

**Input:** path to the (optionally gzipped) JSONL file.

**Output:** `dict[str, dict]`, each value the raw published record.

**Must not:** silently skip malformed lines without at least a blank-line
tolerance — a truncated/corrupt download should fail loudly (`json.loads`
raising is the correct behavior, not swallowed).

**Tests to write:** loads plain `.jsonl`, loads gzipped `.jsonl.gz`, blank
lines are skipped.

## `src/pipeline/selection.py`

**Added after reviewing the real challenge site** to close the last gap
before an actual submission: picking the >=1,000-company corpus. Mirrors the
reference agent's own `select_entry_batch.py`.

**Responsibility:** deterministically sample N org numbers from the loaded
universe manifest.

**Input:** `universe: dict[str, dict]` (from `universe.py`), `count`, `seed`.

**Output:** `list[str]`, sorted, length `min(count, len(universe))`.

**Must:** be reproducible — same `(universe, count, seed)` always produces the
same result, independent of the input dict's iteration order (sort before
sampling), so the submitted manifest can be regenerated byte-for-byte on a
clean checkout.

**Tests to write:** selects the requested count, same seed is deterministic,
different seed can select differently, count >= universe size returns everything.

## `src/pipeline/crawl.py`

**Responsibility:** fetch permitted public pages for a resolved entity.

**Input:** `ResolvedEntity`, remaining request/spend budget from the governor.

**Output:** list of `FetchedPage` — `url`, `raw_html`, `fetched_at`, `fetch_state`.

**Must:**
- Check the budget governor before every request; stop fetching (not the whole
  batch, just this company) once the per-company allocation is spent.
- Try a static fetch first; only escalate to Playwright if the static response
  looks empty/JS-shell (define this check explicitly, don't escalate by default).
- Respect the source policy allow-list (reviewed against the real
  signalpost-sources.md — only the entity's own official-site domain is
  implicitly permitted; anything else needs explicit caller opt-in).
- Classify non-2xx HTTP responses honestly: 404 → `not_available`, 401/403/429
  → `blocked`, 5xx (after capped retries) → `failed`. A non-2xx response must
  never be treated as a successful fetch.

**Must not:**
- Never fetch a URL not covered by the source policy, even if it looks useful.
- Never retry indefinitely — cap retries and record `blocked`/`failed` on give-up.

**Tests to write:** budget-exhausted mid-crawl (→ stops cleanly, partial pages
kept with correct state), JS-shell detection triggers Playwright fallback,
disallowed URL is skipped and logged, not silently fetched, 404/403/5xx are
classified correctly (not treated as available).

**Added after reviewing the real challenge site:** `company_owned_paths`
(opt-in, e.g. `DEFAULT_COMPANY_OWNED_PATHS`) fetches same-domain paths the
agent playbook and learning harness both explicitly prioritise
(`/about`, `/careers`, `/contact`, `/news`, `/investor`, etc.) — same domain
as the official site, no new allow-list risk, and a real coverage lever for
the leadership/hiring/activity sections a homepage alone rarely has.

## `src/pipeline/extract.py`

**Responsibility:** turn raw HTML into structured, unverified facts.

**Input:** `FetchedPage`

**Output:** list of `RawFact` — `field_name`, `value`, `source_url`,
`extraction_method` (`structured` | `text`), `extracted_at`.

**Must:**
- Prefer `extruct` (schema.org/JSON-LD/microdata) before falling back to
  `Trafilatura` text extraction — cheaper and more reliable when available.

**Must not:**
- Never invent a field that wasn't present on the page.

**Tests to write:** page with JSON-LD present (uses structured path), page
without it (falls back to text extraction), malformed HTML doesn't crash the stage.

## `src/pipeline/verify.py`

**Responsibility:** confirm a raw fact actually belongs to the resolved entity.

**Input:** `RawFact`, `ResolvedEntity`

**Output:** `ConfirmedFact` (fact + match confidence + `retrieved_at` carried
through from `RawFact.extracted_at`) or a rejection with reason. `retrieved_at`
was added after the original stub because `docs/data-schema.md` requires it on
every `Claim` with `state="available"`, and `assemble.py` has no other source
for it once a fact reaches this stage.

**Must:**
- Use RapidFuzz name matching against `legal_name` (and known aliases) with an
  explicit, documented threshold. This is the code that enforces the 95%
  precision hard gate — treat threshold changes as gate-risk changes, not minor tuning.

**Must not:**
- Never accept a fact when the source page's company identity doesn't clearly
  match — when in doubt, reject and let the field be `ambiguous`, don't guess.

**Tests to write:** exact name match accepted, near-miss (different company,
similar name) rejected, threshold boundary case documented and tested explicitly.

## `src/pipeline/assemble.py`

**Responsibility:** build the final validated profile from confirmed facts.

**Input:** `ResolvedEntity`, list of `ConfirmedFact`, prior snapshot (if any)

**Output:** `CompanyProfile` (see `data-schema.md`), Pydantic-validated.

**Must:**
- Fill all seven required sections, using an explicit state value for any
  section with no confirmed facts — never omit a section.
- Never let validation fail silently — a schema violation is a bug to fix, not
  a profile to drop from the batch.

**Tests to write:** full data present (all sections populated), sparse data
(missing sections correctly marked `not_available`), schema violation is caught
and raised loudly in tests.

## `src/pipeline/envelope.py`

**Added after reviewing the real challenge site.** `CompanyProfile` is our
internal, validated model; the reference agent's `OUTPUT_CONTRACT.md` defines
the actual submission shape (flat `claims` list, deduplicated `evidence` list
referenced by id, plus `run`/`changes`/`errors`/`operations`). This module
converts one to the other — it's what `run_batch.py`'s CLI writes to the
output JSONL, not `CompanyProfile.model_dump_json()` directly.

**Responsibility:** build one submission envelope per profile.

**Input:** `CompanyProfile`, a `run_id`, optional `operations`/`started_at`/`completed_at`.

**Output:** `dict` matching `OUTPUT_CONTRACT.md`'s shape exactly.

**Must:**
- Deduplicate evidence by `(source_url, content_hash)` — claims sharing a
  source (e.g. two activity signals scraped off one page) share one evidence
  entry, referenced by id, not repeated per-claim.
- Map every section of `CompanyProfile` to a flat claim, including list
  sections (one claim entry per list item).
- Surface `failed`/`blocked` claims in `errors` in addition to `claims`.

**Must not:** drop a claim because it's `not_available`/etc — it still
appears in `claims` (value `null`, empty `evidence_ids`), per the "missing
values are never silently converted to zero" hard gate.

**Tests to write:** available claim produces one claim + one evidence entry,
unavailable claim has no evidence and null value, claims sharing a source
share one deduplicated evidence entry, list fields produce one claim entry
each, material changes pass through, failed/blocked claims appear in errors,
run metadata/operations are included with sensible defaults.

## `src/pipeline/registry_extras.py`

**Added after the initial implementation pass** to close a coverage gap:
`annual_accounts` and `leadership.workplaces` had no wired data source, and
`leadership.leaders` only came from whatever a company's own website happened
to publish. Brønnøysundregisteret — the same official registry `resolve.py`
already queries — separately publishes exactly this data under its own
endpoints, so this stays inside the "Resolve"/official-registry trust tier
rather than becoming a "secondary source" policy question.

**Responsibility:** fetch leadership roles, filed annual accounts, and
registered sub-units (workplaces) for an already-resolved entity, from Brreg's
`roller`, `regnskapsregisteret`, and `underenheter` endpoints respectively.

**Input:** `ResolvedEntity`, `BudgetGovernor`

**Output:** `list[ConfirmedFact]` — already confirmed (`match_confidence=100.0`),
not `RawFact`, because these are fetched by org_number directly against the
official registry that already identified the entity. There is no page to
misattribute, so there is no identity-matching risk for `verify.py` to gate —
routing these through `verify.py` would be a no-op at best and a spurious
rejection risk at worst (registry prose doesn't restate the company name the
way a crawled page does).

**Must:**
- Check `budget` before each of the three calls; skip remaining calls once
  exhausted (same governor, same discipline as `crawl.py`).
- Filter leadership to role groups `DAGL` (CEO) and `STYR` (board); exclude
  `REVI` (auditor) and `VARA` (deputy/alternate) — matches `data-schema.md`'s
  "leaders: e.g. CEO, board chair", not every registered role.
- Exclude deregistered (`avregistrert`) and deceased (`erDoed`) role-holders.
- Never publish a role-holder's date of birth, even though the API returns it
  — not called for by `data-schema.md`, and this is a company-research tool,
  not a personal-data one.

**Must not:**
- Fabricate a value when an endpoint has no data (e.g. a newly-formed company
  with no filed accounts yet) — return no fact for that field, never a guess.
- Retry indefinitely — same capped-retry-then-give-up-cleanly discipline as
  every other network call in this pipeline.

**Tests to write:** leadership roles extracted and correctly filtered (DAGL/STYR
included, REVI/VARA excluded, no birthdate leaked), latest + historical annual
accounts extracted with correct `reporting_period`, workplaces extracted,
budget exhaustion skips remaining calls (not already-fetched ones), no calls
made when the entity wasn't resolved, network failure degrades to no facts
rather than raising.

## `src/storage/cache.py`

**Responsibility:** durable, disk-backed HTTP response cache across runs.

**Must:** cache hits must never count against the request budget (per the
brief: "cache hits free"). Cache key should include URL and a coarse date
bucket so stale-forever caching doesn't hide real changes on refresh.

**Tests to write:** cache hit skips network call and budget decrement; cache
miss performs the call and stores the result; date-bucket expiry works.

---

## `src/storage/snapshots.py`

**Responsibility:** append-only profile storage + refresh diffing.

**Must:** every write is a new row/file keyed by `(org_number, run_timestamp)`.
Refresh reads the latest prior snapshot and produces a `material_changes` list.

**Must not:** never mutate or delete an existing snapshot.

**Tests to write:** running twice back-to-back produces two snapshots, not one
overwritten; diffing correctly ignores trivial/no-op changes (see
`testing-strategy.md` for what counts as "material").

---

## `src/orchestrator/budget.py`

**Responsibility:** the single source of truth for remaining requests, spend,
and wall-clock time in the current batch.

**Must:** expose a check-and-decrement API every other component calls before
spending a resource; expose a "should I degrade now?" signal.

**Tests to write:** governor correctly refuses further spend once any budget
hits zero; simulated near-exhaustion triggers graceful degrade path.

---

## `src/orchestrator/runner.py`

**Responsibility:** wire the stages together for N companies concurrently,
respecting the concurrency model in `architecture.md`.

**Must:** guarantee exactly 100 terminal results are written for a 100-company
batch, even if some companies fail every stage (they still get a profile,
correctly marked with failure states).

**Tests to write:** batch of 100 with a mix of successes/failures still yields
100 output records; concurrency cap is respected under load.

---

## `src/scoring/self_check.py`

**Responsibility:** compute recall/precision/coverage against a hand-labeled
fixture sample, before submission.

**Must:** report the same metric definitions Builderr uses (weighted company
recall, external precision, 70/30 coverage split) so the numbers are directly comparable.

**Tests to write:** known-good fixture scores 100%; known-bad fixture (wrong
company attached) correctly tanks precision in the report.
